## Context

目前圖表顯示流程分散在頁面資料取得、圖表元件初始化與容器尺寸計算三個階段，任一階段失敗都可能讓畫面停在空白且沒有可追蹤訊號。既有程式也缺少對「資料為空」、「初始化時容器不可見」與「資料格式不合法」的一致處理，造成問題難以重現與定位。

## Goals / Non-Goals

**Goals:**
- 建立單一路徑的圖表資料標準化流程，確保圖表輸入資料一定可判斷為可渲染/不可渲染。
- 建立明確的圖表狀態機（loading / ready / empty / error），避免空白區塊無回饋。
- 在容器尺寸尚未穩定時延後或重試渲染，提升首屏顯示成功率。
- 用元件測試鎖定可視化狀態與重渲染行為，降低回歸風險。

**Non-Goals:**
- 不更換圖表函式庫。
- 不修改後端 API 回傳欄位格式。
- 不新增進階技術指標或互動功能。

## Decisions

1. 建立 `normalizeChartData()` 作為圖表唯一輸入入口  
   - **選擇原因**：把資料合法性、欄位對齊、排序與空資料判斷集中處理，可避免每個頁面重複判斷邏輯。  
   - **替代方案**：在各頁面自行轉換資料；缺點是規則分散且容易不一致。

2. 在 `TvChart` 元件內引入顯示狀態列舉並用 computed 派生 UI  
   - **選擇原因**：狀態與畫面一一對應，能明確區分 loading、empty、error，不再出現無訊息空白。  
   - **替代方案**：只靠布林旗標；缺點是狀態組合爆炸，維護成本高。

3. 採用 ResizeObserver + 安全重試初始化  
   - **選擇原因**：容器在切頁或 Tab 顯示切換時常出現寬高為 0，監聽尺寸並在有效尺寸後初始化可提升成功率。  
   - **替代方案**：固定 `setTimeout` 延遲；缺點是依賴時間猜測，裝置差異下不穩定。

4. 錯誤顯示採「可視提示 + console 上下文」雙軌  
   - **選擇原因**：使用者看得到錯誤狀態，開發者可從 log 追蹤來源（資料、初始化、尺寸）。  
   - **替代方案**：僅 console error；缺點是使用者仍只看到空白。

## Risks / Trade-offs

- [ResizeObserver 觸發頻繁] → 以節流與尺寸變化比較避免重複重建圖表。
- [狀態機導入增加元件複雜度] → 將狀態定義集中於型別與單一 computed，維持可讀性。
- [資料正規化過嚴導致可渲染資料被判定無效] → 保留寬鬆模式並在 log 記錄被丟棄欄位，方便調整規則。
- [測試需模擬圖表函式庫] → 使用最小 mock 封裝，避免與第三方實作強耦合。
