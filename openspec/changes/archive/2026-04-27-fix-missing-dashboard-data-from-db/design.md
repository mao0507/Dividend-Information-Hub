## Context

目前儀表板個股圖表在部分情境只顯示標題價格，時間序列為空，根因可能同時包含三類：DB 查詢條件與時間正規化不一致、同步狀態未被前台查詢鏈路感知、前端映射時對缺欄資料過度嚴格而整批捨棄。現況雖已有 `twse-open-data-sync` 與 `stock-price-data-validation` 能力，但尚未把「DB-first 查詢 + 可控回補 + 可診斷錯誤語意」串成一致行為。

## Goals / Non-Goals

**Goals:**
- 建立儀表板行情查詢的 DB-first 資料路徑，DB 有資料時必須直接回傳。
- 當 DB 無資料時，僅在允許條件觸發回補，並回傳可辨識的缺漏原因。
- 前端圖表改為容錯映射，僅過濾壞點，不因單筆缺欄捨棄整段序列。
- 補齊可重現測試，覆蓋 DB 命中、DB 缺漏回補、非交易日與同步未完成情境。

**Non-Goals:**
- 不重寫現有 TWSE 抓取核心流程與排程框架。
- 不新增即時報價資料源或 WebSocket 推送機制。
- 不調整非儀表板相關頁面之圖表元件行為。

## Decisions

1. **查詢鏈路採 DB-first，回補為受控 fallback**
   - 決策：`stock` 查詢服務先以標的與日期範圍查 DB，命中即回傳；僅在「允許回補」且「同步狀態可執行」時觸發回補流程。
   - 原因：避免每次查詢都依賴外部來源，確保延遲與穩定性；同時保留缺漏修復能力。
   - 替代方案：一律先打外部來源再寫回 DB。未採用，因為會放大外部 API 不穩定與節流風險。

2. **錯誤語意標準化為可動作分類**
   - 決策：統一輸出 `NOT_TRADING_DAY`、`MISSING_IN_DB`、`SYNC_NOT_READY`、`SOURCE_UNAVAILABLE`、`VALUE_MISMATCH` 等狀態碼與訊息。
   - 原因：維運可依狀態直接決定「等排程、手動回補、檢查映射」。
   - 替代方案：僅回傳空陣列與通用訊息。未採用，因為無法排障。

3. **前端圖表映射採逐點容錯**
   - 決策：資料轉換以逐筆驗證處理，合法點保留，不合法點標記或略過，並維持可用資料渲染。
   - 原因：避免「一筆壞資料導致全圖空白」。
   - 替代方案：後端強制全量完整才回傳。未採用，因為會降低可見性且增加查詢失敗率。

4. **同步狀態作為查詢決策輸入**
   - 決策：查詢流程讀取同步狀態（最近成功交易日、進度、最後錯誤），決定是否回補與回傳提示。
   - 原因：把資料同步現況顯性化，避免前台誤判系統異常。
   - 替代方案：不讀取同步狀態。未採用，因為難以區分「正常未同步」與「資料異常缺漏」。

## Risks / Trade-offs

- **[Risk] 回補策略過度觸發造成外部來源壓力** → 以開關、日期範圍限制與節流策略保護，並記錄觸發來源。
- **[Risk] 狀態碼增加後前後端契約不一致** → 以 DTO + 測試固定欄位與枚舉，避免自由字串漂移。
- **[Risk] 容錯映射可能掩蓋資料品質問題** → 保留缺失計數與診斷訊息，UI 提示資料品質而非靜默忽略。
- **[Risk] 舊資料時區不一致導致誤判缺漏** → 統一以 `Asia/Taipei` 正規化查詢條件並補測跨時區輸入。
