## Context

目前專案已具備多數頁面與 API 端點雛形，但仍混有展示用假資料、未落地後端流程、以及缺少完整可驗證的 MVP 標準。此變更的核心不是直接新增單一功能，而是建立「可重複執行」的缺口盤點機制，將頁面能力從展示狀態轉為可交付狀態。

主要利害關係人：
- 產品/開發：需要明確知道哪些是 P0 必補、哪些可延後。
- 測試：需要可轉成測試案例的條件，避免主觀驗收。
- 維運：需要確認哪些流程仍依賴假資料或無真實 API。

## Goals / Non-Goals

**Goals:**
- 建立跨頁面基本功能盤點規則，統一檢查「可用性」而非只看 UI 是否存在。
- 將每個核心流程定義為可驗證的 MVP 條件（輸入、行為、輸出、錯誤處理）。
- 產出 P0/P1/P2 缺口清單與可直接實作的任務模板（前端/後端/資料/測試）。
- 建立可追蹤的輸出格式，確保後續每次盤點都可比較差異。

**Non-Goals:**
- 本文件不直接實作所有缺口修復。
- 不在此階段重做 UI 視覺設計。
- 不強制一次完成所有次要（P2）優化項目。

## Decisions

1. **以核心使用者旅程作為盤點主軸，而非頁面主軸**
   - 決策：以「登入→儀表板→自選→提醒→設定→搜尋」的任務完成鏈路盤點。
   - 理由：單看頁面容易忽略跨頁資料一致性與流程中斷點。
   - 替代方案：逐頁 checklist。缺點是跨頁依賴常被漏檢。

2. **缺口分類採四象限：功能缺失 / 串接缺失 / 資料真實性 / 驗收缺失**
   - 決策：每個缺口都必須落在至少一個分類。
   - 理由：可直接映射給前端、後端、資料、測試責任域。
   - 替代方案：單一缺陷列表。缺點是優先序與責任不清晰。

3. **優先級採 P0/P1/P2，並要求 P0 必含可驗證驗收條件**
   - 決策：P0 必須同時描述「失敗風險」與「驗收步驟」。
   - 理由：避免高優先級項目仍停留在抽象描述。
   - 替代方案：僅用高/中/低。缺點是無法直接推導實作排程。

4. **輸出為 OpenSpec 任務導向，確保可直接 apply**
   - 決策：盤點結果必須對應到可執行 task（含 owner domain 與測試要求）。
   - 理由：避免「只有報告沒有落地」。
   - 替代方案：僅產出審查報告。缺點是後續落地成本高且易遺失脈絡。

## Risks / Trade-offs

- **[Risk] 盤點範圍過大導致時程拉長** → 先聚焦 P0 核心旅程，P1/P2 以 backlog 形式延後。
- **[Risk] 缺口描述仍過於主觀** → 每個缺口強制附「可重現步驟 + 預期結果 + 實際結果」。
- **[Risk] 任務過度細碎造成管理負擔** → 任務切分以「可獨立驗收」為準，不做過度拆分。
- **[Risk] 盤點完成後未實作** → 每個 P0 缺口需綁定後續 task owner 與驗收測試類型。
